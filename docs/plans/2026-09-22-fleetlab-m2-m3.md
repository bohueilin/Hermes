The user explicitly authorized M2, M3, testing, repository updates and conditional live
publication on 2026-09-22. This supersedes the earlier M1-only/no-publishing limit.
Implementation stays in the existing isolated website-lineage worktree. The source

M4, optional tasks, concurrent scheduling, taper, tariffs and physical simulation remain deferred.

## Intent and design

A reviewer should distinguish useful power from occupied plugs, decide whether a
charging policy changes readiness/service, see why a resource is not eligible, and
compare forecast preparation against reactive service without future-demand leakage.
Every new feature is opt-in and versioned. No framework, dependency, backend, live
feed or Python evidence integration is introduced. Historical/M1 whole-result pins
remain authoritative. All browser outputs are NOT_EVIDENCE with no execution authority.

- `charging-allocation.js`: battery-side kW, efficiency 1 and no auxiliary demand,
  preserving legacy accounting. Equal-share; capped water-filling redistribution;
  deadline-priority allocation/queue order with oldest-task priority beyond a declared
  starvation age. Stable vehicle-ID deadline tiers are assigned when visits begin.
  Validate proposed power before energy mutation. Terminal intervals deliver zero.
- `resource-observations.js`: fictional per-site charging-port IDs; planned/installed/
  commissioned/healthy/compatible truth separate from sequenced delayed observations.
  Reject duplicate/out-of-order observations; unknown is unavailable. Last-known and
  freshness-aware policies differ only in planner eligibility. Execution always checks
  current truth and ownership. Window-long leases preserve ownership across outages;
  unhealthy connected vehicles receive zero power and recover when truth permits.
- `airport-demand.js`: synthetic SFO arrivals, passenger-ready delay/spread and keyed
  conversion/destination draws. Intake cutoff is distinct from observation end. An
  independently supplied, published/expiring forecast drives bounded preparatory
  relocation using existing routes/energy. Preparation slots include inbound vehicles;
  trip assignment releases them. No actual access permission is represented.
- Bay engine hooks: optional records, resource reservations, allocator, airport request
  generation and preparation movement. Rendering consumes recorded state only.
- `bay-experiment-contract.js` plus existing `model/experiment.js`: exact single-axis
  paired experiments; disjoint tuning/evaluation seeds; repeated-run check; explicit
  metric producer/population/version validation and required-measurement availability
  before reusing existing paired/bootstrap math. No cross-model pooling. Primary
  completion fraction; practical margin in fraction units. Guardrails include wait,
  unfinished work, terminal energy, non-airport service and rejected actions. One seed
  is descriptive with no interval. Intervals describe this synthetic model only.
- `advanced-operations-view.js`: controls/presets, recorded power/resource/forecast
  detail, comparison progress, all request dispositions, named guardrails, exact JSON.
  Clear stale comparisons on any edit. Native tables and offline packaging remain.

## Review focus

Missing vs zero data; stranded/inbound work at horizon; stale observation that lies
about health/commissioning; forecast leakage into demand realization; energy or task
work created by extra terminal frames; unavailable guardrails wrongly defaulting to a
pass; interrupted/pending UI runs; hidden overflow of exact-value disclosures; cross-
model result acceptance. Tests explicitly cover these inputs.

## Release gate

No failing correctness, boundary or package tests; existing opt-in skips/TODO are
reported and their applicable checks exercised; no unresolved security findings in
reviewed scope. A clean scan means no findings detected, not proof of zero risk.
The release is a static teaching application, not operational approval.
