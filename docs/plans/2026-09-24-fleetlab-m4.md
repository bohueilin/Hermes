# FleetLab M4 and scenario learning implementation plan

> Execute with the existing isolated worktree and the subagent development/review workflow. The user explicitly authorized completion and publication of M2/M3/M4 on 2026-09-24. This supersedes prior M4 deferral; it does not authorize a backend or physical operations.

**Goal:** Visitors can configure a second region, identify incomplete depot setup, rehearse commissioning delays using the existing Fleet day engine, and explain each scenario's fleet-optimization decision and measured trade-offs.

**Architecture:** Add an explicit `depot-launch-1.0.0` extension with versioned region/depot data. Keep historical Bay preparation and fixtures untouched when absent. A launch contract supplies geometry, fixed depot/resource identities, capabilities, calendars, setup ownership/dependencies and sequenced mock commissioning events to the existing lifecycle. A native JavaScript panel within Fleet day projects validation, two recorded runs and replay tables. No new simulator, library, backend, telemetry, account, or operational authority.

**Specification:** Revision 2.0 brief B5/M4 plus the current user goal. B2/B3/minimum B4 remain implemented; charge taper, optimized universal scheduling and physics remain deferred. The learning requirement covers M1–M4 and preserves separate Street lab and regional metric populations.

## Contracts and decisions

- `RegionConfig` 1: bounded identity/name, local timezone label and synthetic date/calendar, 2–18 places, explicit compatible geography type. Peninsula uses selected frozen Bay routes; Region B uses explicitly synthetic kilometer geometry and distances. No invented OSM provenance or current expansion claim.
- `DepotConfig` 1: stable ID and anchor, per-site power/stage/worker capacity, finite named ports with installation/commissioning/health/compatibility, local opening window, owned setup tasks with acyclic dependencies.
- Mock event schema 1: event identity, site/resource identity, sequence, effective minute and commissioning change. Reject malformed, duplicate, reordered, unowned or dependency-violating actions with named checks; never grant execution capacity through an invalid event. Rejected actions are distinct from invalid simulator state.
- In-process exports from `model/launch-rehearsal.js`: `createLaunchConfig(template)`, `validateLaunchConfig(config)`, `compareCommissioning(config, delayMinutes)`. Validation returns `{ok, checks, summary}`; comparison returns `{format, version, evidence_status, deployment_permission, descriptive, validity, reason, spec, baseline, candidate, comparison}`. Both arms use the same fleet, demand, rules and resource identities; only effective commissioning times change. One seed is descriptive, with all-request pickup-target, completion, unfinished visits/tasks, queue/active and terminal energy populations shown.
- Baseline and candidate are full existing-engine recorded results. The adapter must reject incompatible launch versions/regions, absent populations and changed external demand. Setup metrics are simulated configuration/task counts, never measured operator adoption or usability.
- Rehearsal runs only after structural validation; pending commissioning remains an explicit setup blocker that can be rehearsed. Site hours constrain new task acquisition and power; already active non-charging tasks finish nonpreemptively. Calendars use bounded declared local minutes, not a timezone/DST service.
- A compact learning guide will state question, treatment, fixed inputs, result population, possible trade-offs and next experiment for each new situation. Dynamic lessons derive from recorded comparisons, with no fixed winner or advertised percentage.

## Review focus

1. Pending or physically absent infrastructure must not become usable because a setup task or planner says ready.
2. Resource IDs, region routes and selected depot anchors must stay aligned; no implicit fallback to Bay geometry for Region B.
3. Comparing another commissioning time must not consume different random draws or hide pending requests.
4. A calendar boundary or terminal frame must not create energy or release mandatory unfinished work.
5. Template changes and edits during a run invalidate pending/current UI results; text and exports remain inert and model-specific.
